# Moriarty overlap and Midnight backend options

Context pointer: [Wayfinder ticket, Assess Moriarty and Midnight backend paths](https://github.com/awjreynolds/noctium/issues/7)

Checked 2026-11-16 against Moriarty `main` at commit [`4ea6fa2`](https://github.com/CharlesHoskinson/Moriarty/commit/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2) and official Midnight documentation. This is source and documentation review. I did not build or run Moriarty.

## Findings

Moriarty now has a real direct-ZKIR compiler path. Its native Rust profile, `language "moriarty/1";`, parses a bounded financial language into a checked expression representation, supports local reference execution, and lowers admitted programs to upstream-readable `.zkir`. Its Rust CLI exposes `compile`, `simulate`, manifest-based `test`, `intent`, and `verify-intent`. The separate TypeScript beta uses other profiles and does not provide this Rust compiler. [README, native language section](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/README.md#L60-L66) [Native core guide](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/docs/NATIVE-CORE.md)

The overlap is in a backend and in bounded circuit concepts, not in the source language. Moriarty's `mori-core::Program` and `mori-backend` compile financial actions, public inputs, state frames, guards, transfers, fees, events, and liability operations. Its current Core profile uses UInt and Bool expressions, checked 128-bit financial amounts, and a closed action statement set. It excludes general loops, branch statements, records, division, and dynamic account selection. This is a narrow financial language, not a general Lean expression backend. [Core language reference](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/crates/mori-core/README.md) [Backend crate](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/crates/mori-backend/Cargo.toml) [Compiler command](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/crates/mori/src/commands/compile.rs)

Some backend evidence is substantive but bounded. The repo reports upstream ZKIR deserialization and compatibility tests, one local selected signed native proof that was independently verified, and a three-step Sherlock recursion proof checked with the ledger 9.1.0.1 verifier library. It also says no ledger 9.1.0.1 node has accepted the Sherlock contract transaction, the candidate native call proving APIs have not run through key generation, proving, or cryptographic verification, and complete compiler correspondence, authenticated state/history, settlement, and deployment remain open. The project labels itself experimental and not a production SDK or audited deployment. [Native core guide, evidence and open gates](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/docs/NATIVE-CORE.md#L450-L475) [Native call proving qualification](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/docs/NATIVE-CALL-PROVING.md#L1-L5) [README, current project status](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/README.md#L7-L15) [README, Sherlock status](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/README.md#L391-L419)

There is a version qualification to resolve before treating Moriarty's checked-in target as qualified against a current network profile. Moriarty's workspace pins the ledger 9.1.0.1 sources and `midnight-zkir` 3.2.0, while its `mori-backend::Target` and example target descriptor require ledger revision `04c9c5d…` and ZKIR `3.0.0-rc.2`. The ledger documentation reviewed on 2026-11-16 identified ZKIR 3.2.0; Compact 0.36 emits ZKIR 3.1 using a 3.2.0-rc.2 compiler binary. The [updated baseline](compact-equivalence-baseline.md) records the 2026-11-17 client patch. These are distinct version identifiers, so the mismatch alone does not prove incompatibility. Moriarty's exact emitted IR and artifact still need qualification against the selected ledger and deployment route. [Current compatibility matrix](https://docs.midnight.network/relnotes/support-matrix) [Moriarty workspace pins](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/Cargo.toml) [Target validation](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/crates/mori-backend/src/lib.rs#L1-L115) [Moriarty target descriptor](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/toolchains/ledger-9.json) [Ledger 9.1.0.1 notes](https://docs.midnight.network/relnotes/ledger/ledger-9-1-0-1) [Compact 0.36 notes](https://docs.midnight.network/relnotes/compact/toolchain-0.36.0)

The backend is Apache-2.0 and lives in a Rust workspace package currently marked `0.1.0`; its public entry point is `compile(&Program, &Target)`. The reviewed docs promise no versioned external API stability. Reuse through a pinned Git dependency or adapter couples Noctium to Moriarty's AST, compiler revisions, and maintenance cadence. [Workspace license and dependencies](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/Cargo.toml) [Backend package](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/crates/mori-backend/Cargo.toml) [Public compile entry point](https://github.com/CharlesHoskinson/Moriarty/blob/4ea6fa29d5aed68c8aeabfea1b6a611e611df7e2/crates/mori-backend/src/lib.rs#L360)

## Backend comparison

| Path | Evidence and fit | Main cost or open gate |
| --- | --- | --- |
| Reuse Moriarty's Rust backend | Existing ZKIR lowering, bounded relation model, native tests, and selected local proof evidence. Moriarty can serve as a comparison tool for a Lean-owned representation and emitted IR. | A required Rust backend conflicts with the user's decision that Noctium itself be implemented in Lean. Moriarty's front end defines financial semantics, its API has no reviewed stability promise, and its checked-in target identifier needs reconciliation with current ledger 9. |
| Own a Lean ZKIR backend | Keeps Noctium's compiler implementation, semantics, typed circuit representation, and ledger-derived capability boundary in Lean. Moriarty and `midnight-zkir` offer useful reference material for instruction emission and compatibility checks. | Requires Lean-owned typed lowering, public-input binding, relation constraints, artifact formats, and compatibility tests. Producing `.zkir` and keys alone does not establish the contract bundle or deployment path. |
| Compact adapter | Midnight documents a complete route from Compact source to `zkir/`, `keys/`, and generated contract bindings. It is a useful adapter for capabilities whose semantics map exactly to Compact. | It cannot define Noctium's language boundary. A Compact-only path would exclude capabilities unavailable through Compact even if the selected ledger/proving interfaces expose them. Source-to-Compact equivalence and the generated bundle still need tests. |

The compatibility matrix checked on 2026-11-16 listed Compact 0.36.0, language 0.28.0, Compact runtime 0.21.0, on-chain runtime 4.0.0, and proof server 9.0.0 for public ledger 9. The [updated baseline](compact-equivalence-baseline.md) records the 2026-11-17 client patch. The 0.36.0 Compact release states that its compiler emits ZKIR 3.1 and bundles `midnight-zkir` 3.2.0-rc.2. The official ZKIR repository supplies IR types, a VM, and `zkir compile`/`compile-many` to produce proving and verifying keys. The reviewed ZKIR docs do not define a complete direct-ZKIR contract package with Midnight.js bindings and deployment metadata. [Current compatibility matrix](https://docs.midnight.network/relnotes/support-matrix) [Ledger 9 compatibility notes](https://docs.midnight.network/relnotes/ledger-9) [ZKIR repository](https://github.com/midnightntwrk/midnight-zkir) [Compact build output](https://docs.midnight.network/guides/build-a-private-smart-contract) [Deployment guide](https://docs.midnight.network/guides/deploy-and-operate)

## Recommendation

Implement Noctium's frontend, semantic checks, typed circuit representation, compiler passes, and primary ZKIR lowering in Lean 4, as the user specified. Derive its source semantics from the selected ledger 9 and proving interfaces. Treat Moriarty as a reference implementation and comparison tool, not a required Rust compiler component or normative language. Before committing to a final artifact route, run a bounded compatibility spike: lower one selected Noctium workload in Lean, validate the emitted IR with the selected ledger 9 toolchain, generate and verify a proof, assemble contract artifacts, and test deployment on Preview. Resolve target-version identifiers during that spike.

Keep Compact as an optional artifact adapter for selected constructs where lowering preserves Noctium semantics. Do not use Compact's feature list to set source scope. A Compact adapter may help fill artifact or deployment gaps, but its translator remains Lean code and must preserve Noctium's semantics. The final artifact route waits on the first workload and version checks.

## Unverified

- I did not run Moriarty's build, test suite, compiler, proof commands, or deployment workflow.
- I did not verify a full ledger 9 Noctium-to-ZKIR-to-deployment bundle from any non-Compact frontend.
- The target-version mismatch is a source inspection finding; compatibility impact needs a real compile, proof, and network acceptance check.
